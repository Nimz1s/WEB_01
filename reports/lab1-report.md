##1. Виконання роботи

## 1.1. Налаштування проєкту

У межах лабораторної роботи було розпочато розроблення backend-частини вебзастосунку TableBook, призначеного для онлайн-бронювання столиків у ресторанах.
Для реалізації серверної частини використано платформу Node.js та фреймворк Express.js.
Під час налаштування проєкту виконано такі завдання:
-Створено Node.js-проєкт за допомогою npm.
-Встановлено необхідні залежності для роботи серверної частини.
-Налаштовано Express.js для обробки HTTP-запитів.
-Створено структуру каталогів для контролерів, маршрутів, middleware, конфігурацій та валідаторів.
-Налаштовано змінні середовища за допомогою бібліотеки dotenv.
-Підключено middleware для обробки JSON-запитів, CORS, захисту HTTP-заголовків та журналювання запитів.

Основні використані технології та бібліотеки:

Node.js — серверне середовище виконання JavaScript.
Express.js — фреймворк для створення REST API.
PostgreSQL — система керування реляційними базами даних.
Prisma ORM — інструмент взаємодії з базою даних.
Zod — бібліотека для валідації вхідних даних.
dotenv — керування змінними середовища.
Helmet — захист HTTP-заголовків.
CORS — налаштування міждоменного доступу.
Morgan — журналювання HTTP-запитів.
Swagger UI та swagger-jsdoc — документування API.

## 1.2. База даних

Для зберігання інформації про ресторани, користувачів, столики та бронювання налаштовано PostgreSQL.
Для взаємодії з базою даних використано Prisma ORM. Створено файл prisma/schema.prisma, у якому описано структуру моделей, їхні поля, типи даних, обмеження та зв'язки.
У базі даних передбачено такі основні моделі:

User — користувачі системи. Містить ім'я, електронну пошту, хеш пароля та роль користувача.
Restaurant — ресторани. Містить назву, опис, адресу, контактний телефон та посилання на зображення.
RestaurantTable — столики ресторанів. Містить номер столика, місткість та стан доступності.
Booking — бронювання столиків. Містить користувача, столик, дату й час бронювання, кількість гостей та статус бронювання.
Category — категорії ресторанів.
Review — відгуки користувачів про ресторани.
Favorite — обрані ресторани користувачів.

У схемі бази даних передбачено зв'язки між сутностями:

User — Booking: зв'язок один-до-багатьох.
Restaurant — RestaurantTable: зв'язок один-до-багатьох.
RestaurantTable — Booking: зв'язок один-до-багатьох.
User — Restaurant: зв'язок один-до-багатьох для власників ресторанів.
User — Restaurant та Restaurant — User: зв'язок багато-до-багатьох через модель Favorite.
Restaurant — Category: зв'язок багато-до-багатьох.

Також визначено перелік ролей користувачів: CUSTOMER, RESTAURANT_ADMIN та SYSTEM_ADMIN, а для бронювань — статуси PENDING, CONFIRMED, CANCELLED та COMPLETED.
Схему Prisma було відформатовано та перевірено на коректність. Виконано налаштування підключення до PostgreSQL та створення таблиць бази даних.

## 1.3. Backend архітектура

Для серверної частини створено Express.js сервер, який забезпечує обробку запитів клієнта та взаємодію з базою даних.
У проєкті використано принципи MVC-архітектури (Model-View-Controller):

Models: структури даних та моделі Prisma.
Controllers: логіка обробки запитів і взаємодії з базою даних.
Routes: визначення API-маршрутів та підключення відповідних контролерів.

Реалізовано такі middleware:

validate.js — перевірка вхідних даних за допомогою Zod.
errorHandler.js — централізована обробка помилок.
helmet() — налаштування захисних HTTP-заголовків.
cors() — налаштування CORS.
express.json() — обробка JSON-тіла запитів.
morgan('dev') — журналювання HTTP-запитів.

Для валідації створено окремі схеми ресторану та столика. Перевіряються обов'язкові поля, типи даних, мінімальна та максимальна довжина рядків, коректність UUID та числових значень.
Також реалізовано обробку типових помилок Prisma, зокрема порушень унікальності записів, відсутності записів та порушень зовнішніх ключів.

## 1.4. API endpoints

У межах лабораторної роботи реалізовано REST API для керування ресторанами та столиками.

API для ресторанів — /api/restaurants
HTTP-метод
Endpoint
Призначення

GET
/api/restaurants
Отримання списку всіх ресторанів

GET
/api/restaurants/:id
Отримання ресторану за ідентифікатором

POST
/api/restaurants
Створення нового ресторану

PUT
/api/restaurants/:id
Оновлення інформації про ресторан

DELETE
/api/restaurants/:id
Видалення ресторану

API для столиків — /api/tables
HTTP-метод
Endpoint
Призначення

GET
/api/tables
Отримання списку всіх столиків

GET
/api/tables/:id
Отримання столика за ідентифікатором

POST
/api/tables
Створення нового столика

PUT
/api/tables/:id
Оновлення інформації про столик

DELETE
/api/tables/:id
Видалення столика

Для створення та оновлення записів реалізовано перевірку вхідних даних. Некоректні запити повертають відповідь зі статусом HTTP 400 та описом помилок валідації.
У разі успішного створення запису повертається HTTP 201, успішного отримання або оновлення — HTTP 200. Для відсутніх записів передбачено HTTP 404.

## 1.5. Документування API

Для документування серверного API використано Swagger UI та swagger-jsdoc.
Створено конфігураційний файл src/config/swagger.js, у якому визначено версію OpenAPI, назву API, його опис та адресу локального сервера.
Документацію підключено до Express за адресою:

http://localhost:3000/api-docs

У Swagger описано 10 операцій для роботи з ресторанами та столиками. Документація дозволяє переглядати доступні endpoints, їхні параметри та виконувати HTTP-запити безпосередньо через браузер.

## 1.6. Тестування API

Для перевірки працездатності серверної частини використовувалися PowerShell та Swagger UI.
Під час тестування було виконано такі перевірки:

Перевірено запуск Express-сервера та доступність головного маршруту.
Перевірено отримання списку ресторанів через GET-запит.
Створено ресторан Bella Italia через POST-запит.
Перевірено отримання створеного ресторану.
Виконано оновлення опису ресторану через PUT-запит.
Перевірено валідацію даних: сервер правильно виявив некоректну назву та адресу ресторану.
Перевірено отримання списку столиків.
Створено столик №1 для ресторану Bella Italia.
Перевірено збереження столика та зв'язок із відповідним рестораном.
Перевірено роботу Swagger UI та виконання GET-запиту до /api/restaurants.

Під час тестування отримано успішну HTTP-відповідь 200 для запиту GET /api/restaurants. Сервер повернув дані ресторану Bella Italia, збережені в PostgreSQL.

Також перевірено створення записів із використанням Prisma ORM та автоматичне формування UUID і часових позначок створення й оновлення.

## 4. Висновки

Під час виконання лабораторної роботи було розроблено основу backend-архітектури вебзастосунку TableBook — системи онлайн-бронювання столиків у ресторанах.
Було налаштовано середовище Node.js, створено сервер на базі Express.js та організовано підключення до PostgreSQL за допомогою Prisma ORM.
Розроблено структуру бази даних із пов'язаними моделями користувачів, ресторанів, столиків, бронювань, категорій, відгуків та обраних ресторанів.
Реалізовано CRUD-операції для ресторанів і столиків, налаштовано маршрутизацію, валідацію вхідних даних за допомогою Zod та централізовану обробку помилок.
Для документування API інтегровано Swagger UI, що забезпечує можливість перегляду та тестування реалізованих endpoints.
У процесі роботи було отримано практичні навички розроблення серверної частини вебзастосунку, роботи з реляційними базами даних, використання ORM, побудови REST API та документування програмного інтерфейсу.
