## 3. Хід виконання роботи

## 3.1. Інтеграція Socket.io

До серверної частини TableBook інтегровано Socket.io.
Для роботи з WebSocket створено окремий модуль src/socket/index.js.
Socket.io підключено до HTTP-сервера, створеного на основі Express. Реалізовано обробку підключення та відключення користувачів.
Для автентифікації WebSocket-з'єднань створено middleware socketAuth.js, який перевіряє JWT-токен, переданий клієнтом під час підключення.
Якщо токен відсутній, недійсний або прострочений, підключення відхиляється.

## 3.2. Система кімнат (Rooms)

Для групування користувачів реалізовано персональні та групові кімнати:

user:{userId} — персональна кімната користувача;
restaurant:{restaurantId} — кімната конкретного ресторану.
Кожен автентифікований користувач автоматично приєднується до власної персональної кімнати.
Для приєднання адміністратора ресторану до кімнати перевіряється його роль та право власності на відповідний ресторан.
Це дозволяє надсилати повідомлення конкретному користувачу або адміністраторам певного ресторану.

## 3.3. Оновлення в реальному часі

У TableBook реалізовано передачу подій, пов'язаних із бронюваннями.

Основні події:

booking:new — повідомлення про створення нового бронювання;
notification:new — отримання нового персонального сповіщення;
user:status — зміна онлайн-статусу користувача.

Під час створення бронювання сервер може надіслати повідомлення до кімнати відповідного ресторану.
Після зміни статусу бронювання користувача створюється персональне сповіщення, яке надсилається через Socket.io до кімнати цього користувача.

## 3.4. Онлайн-статус користувачів

Для відстеження онлайн-статусу використовується структура Map у пам'яті сервера.
Вона зберігає кількість активних Socket.io-з'єднань кожного користувача.
При першому підключенні користувача генерується подія user:status зі статусом ONLINE.
Коли останнє з'єднання користувача закривається, генерується подія зі статусом OFFLINE.
Такий підхід враховує ситуацію, коли один користувач підключений із кількох вкладок або пристроїв.

## 3.5. Система сповіщень

Створено модель Notification у Prisma Schema.
Модель містить такі поля:

id — унікальний ідентифікатор;
userId — ідентифікатор отримувача;
type — тип сповіщення;
message — текст повідомлення;
isRead — ознака прочитання;
createdAt — дата створення.

Створено контролер notificationController.js та маршрути notificationRoutes.js.
Реалізовано такі API-ендпоінти:

GET /api/notifications — отримання сповіщень поточного користувача;
PATCH /api/notifications/:id/read — позначення сповіщення як прочитаного.

Користувач може отримувати лише власні сповіщення. Для цього використовується ідентифікатор із JWT-автентифікації.
Також реалізовано збереження сповіщень у PostgreSQL та їх доставку через Socket.io.

## 3.6. Оптимізація бази даних

Для покращення продуктивності бази даних додано індекси в Prisma Schema.
Для моделі бронювання створено індекси:

[userId, startsAt];
[tableId, startsAt, endsAt];
[status, startsAt].

Для моделі сповіщень створено індекси:

[userId, isRead];
[createdAt].

Ці індекси призначені для прискорення пошуку бронювань за користувачем, столиком, статусом та датою, а також отримання сповіщень користувача.
Створено та застосовано міграції Prisma:

add_notifications;
add_booking_indexes.

## 5. Відповіді на контрольні запитання

### 1. Чим WebSocket відрізняється від HTTP та від періодичного опитування (polling)? Коли WebSocket виправданий, а коли достатньо звичайних HTTP-запитів?

HTTP працює за моделлю запит-відповідь: клієнт надсилає запит, а сервер повертає відповідь.
Polling — це періодичне надсилання клієнтом HTTP-запитів для перевірки наявності нових даних. Такий підхід створює додаткове навантаження, навіть якщо змін немає.
WebSocket забезпечує постійне двостороннє з'єднання, через яке сервер і клієнт можуть обмінюватися повідомленнями в будь-який момент.
WebSocket доцільно використовувати для миттєвих сповіщень, онлайн-чатів, оновлення бронювань та статусів користувачів. Для звичайних операцій CRUD, реєстрації та авторизації достатньо HTTP-запитів.

### 2. Що додає Socket.io порівняно з «чистим» WebSocket? Чому клієнт Socket.io не може підключитися до звичайного WebSocket-сервера?

Socket.io додає до WebSocket автоматичне повторне підключення, кімнати, події, підтвердження отримання повідомлень та можливість переходу на HTTP long-polling.
Socket.io використовує власний протокол поверх WebSocket і додатковий механізм обміну повідомленнями.
Тому клієнт Socket.io не може напряму працювати зі звичайним WebSocket-сервером. Для цього потрібен сумісний сервер Socket.io.

### 3. Чим відрізняються кімнати (rooms) від просторів імен (namespaces)? Як ви використали кімнати у своєму проєкті?

Rooms — це групи Socket.io-з'єднань усередині одного простору імен. Вони використовуються для надсилання повідомлень певній групі клієнтів.
Namespaces — це логічно відокремлені канали всередині одного Socket.io-сервера, які можуть мати власні обробники подій та middleware.
У TableBook використовуються кімнати user:{userId} для персональних повідомлень і restaurant:{restaurantId} для групування підключень, пов'язаних із конкретним рестораном.

### 4. Як у вашому застосунку автентифікуються WebSocket-з'єднання? Що відбувається, коли токен доступу спливає під час активного з'єднання?

Під час підключення клієнт передає JWT-токен у параметрі auth.token.
Сервер використовує middleware socketAuth.js, який перевіряє токен за допомогою jsonwebtoken та секрету JWT_SECRET.
Якщо токен відсутній або недійсний, підключення відхиляється.
Після завершення строку дії токена активне WebSocket-з'єднання автоматично не закривається лише через спливання JWT. Для продовження роботи клієнт повинен отримати новий access token за допомогою механізму оновлення токенів і перепідключитися з новим токеном.

### 5. Як клієнт відновлює стан після втрати з'єднання та повторного підключення? Які події можуть бути пропущені?

Socket.io підтримує автоматичне повторне підключення після втрати з'єднання.
Після перепідключення клієнт може повторно отримати актуальні дані через HTTP API, наприклад список бронювань або сповіщень.
Під час розриву з'єднання клієнт може пропустити події про створення бронювання, зміну статусу або нові сповіщення.
У поточній реалізації TableBook автоматичне перепідключення забезпечується Socket.io, а актуальні збережені сповіщення можна отримати через API. Окремий механізм збереження історії всіх WebSocket-подій та відновлення пропущених подій за їхніми ідентифікаторами ще не реалізований.

### 6. Як працює B-tree індекс? За якими критеріями ви обирали колонки для індексування і яка ціна індексів?

B-tree — це збалансована деревоподібна структура даних, яка дозволяє швидко знаходити записи за значенням або діапазоном значень.
Колонки для індексування обирають за частотою використання в умовах WHERE, JOIN та ORDER BY.
У TableBook індекси створено для пошуку бронювань за користувачем, столиком, статусом і часом, а також для пошуку сповіщень за користувачем та ознакою прочитання.
Недоліком індексів є додаткове використання дискового простору та уповільнення операцій INSERT, UPDATE і DELETE, оскільки індекси потрібно оновлювати разом із даними.

### 7. Що таке проблема N+1? Як ви її виявили та усунули за допомогою Prisma?

Проблема N+1 виникає, коли спочатку виконується один запит для отримання списку записів, а потім для кожного запису окремо виконується ще один запит для отримання пов'язаних даних.
Наприклад, отримання списку бронювань і окремий запит для кожного бронювання, щоб отримати інформацію про користувача.
У Prisma для зменшення кількості запитів використовують include та select, які дозволяють отримувати пов'язані дані разом з основними записами.
У межах цієї лабораторної роботи додано індекси, однак повний аналіз і документоване усунення N+1 проблеми не проводилися.

### 8. Що показує EXPLAIN ANALYZE? Чим Seq Scan відрізняється від Index Scan?

EXPLAIN ANALYZE показує план виконання SQL-запиту та фактичний час його виконання.
Seq Scan означає послідовне сканування рядків таблиці. Це може бути повільно для великих таблиць.
Index Scan означає використання індексу для пошуку потрібних записів, що часто дозволяє зменшити кількість прочитаних рядків.
Використання індексу не завжди швидше: для запитів, які повертають значну частину таблиці, PostgreSQL може обрати Seq Scan.
У цій роботі створено індекси, але порівняння планів EXPLAIN ANALYZE до та після індексування окремо не виконувалося.

### 9. Навіщо потрібен Redis-адаптер під час горизонтального масштабування Socket.io? Чому за кількох екземплярів сервера потрібні «липкі» сесії (sticky sessions)?

Якщо Socket.io працює на кількох екземплярах сервера, кожен екземпляр має власні кімнати та підключення в пам'яті.
Redis-адаптер дозволяє передавати повідомлення між різними екземплярами сервера через спільний канал обміну даними.
Sticky sessions потрібні, коли використовуються HTTP long-polling-запити: вони допомагають спрямовувати запити одного клієнта до того самого екземпляра сервера, на якому створено його сесію.
У поточній версії TableBook використовується один екземпляр сервера, Redis-адаптер і горизонтальне масштабування не реалізовані.

### 10. Які обмеження безкоштовного тарифу вашого хостингу ви врахували? Чим prisma migrate deploy відрізняється від prisma migrate dev?

Для безкоштовного хостингу потрібно враховувати можливе автоматичне засинання сервісу, затримку першого запиту після простою, розрив WebSocket-з'єднань, тимчасову файлову систему та обмеження терміну зберігання бази даних.
У цій роботі зовнішній хостинг ще не обрано, тому фактичні обмеження конкретного тарифу не перевірялися.
prisma migrate dev використовується під час розробки: команда створює та застосовує міграції, а також призначена для роботи з локальною базою даних.
prisma migrate deploy застосовує вже створені міграції до робочої бази даних. Цю команду використовують під час розгортання застосунку в production-середовищі.
